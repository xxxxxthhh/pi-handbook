§1 Mental Model 一句话心智模型

先记住这一句

pi 是一个「三层核心 + 一堆试验性外围」的仓库：ai 管 provider，agent 管循环，coding-agent 管产品——这三个包占了 81% 的代码。其余七个包加起来不到两成，且多数标着 experimental。

§3 Design 设计动机与权衡

为什么 coding-agent 这么大

12 万行里装的是：7 个内建工具、扩展系统、交互模式的全部 UI 组件、会话管理、设置系统、主题、键位、RPC/JSON 模式、导出 HTML……换句话说，凡是「产品决策」都在这一层。

这与 CONTRIBUTING.md 的声明是一致的：核心要最小，不属于核心的应该做成扩展。CONTRIBUTING.md:9 但要注意「核心」在这句话里指的是 packages/agent（2 万行），不是 coding-agent。coding-agent 本身不受这条约束——它是产品。

自研 TUI 这个决定

3.2 万行手写一个终端 UI 库，而不是用 Ink（React for CLI）或 blessed。代价是显然的；收益要到 第 11 章才说得清。这里先记一个事实：tui 包零内部依赖，也不依赖 React——它是这个仓库里最容易被单独复用的部分。

experimental 的自我标注

server 包的 README 第一句就是：Experimental. 本包处于活跃开发中，可能变更或移除，恕不另行通知；API 与行为尚不稳定。server/README.md:3

把稳定性承诺写在 README 第一行，比藏在版本号里诚实。对照 第 07 章提到的「唯一兼容承诺」，这是同一种做法：把变更自由度显式声明出来，而不是靠 semver 暗示。

§4 Limits 边界与失效条件
  • 行数统计包含测试与生成文件。tools/stats.sh 统计的是 packages/*/ 下全部 .ts/.tsx，不区分 src 与 test。真实的「产品代码」比表里的数字小。
  • 286 位作者是按署名去重的。同一个人用多个 email 会被合并，但不同人重名不会被拆开。这是个近似值。
  • 月均 428 提交是简单平均。首尾月份不完整，且 2026-01 单月有 1224 次提交（明显的异常高峰），平均值掩盖了这种波动。
  • 依赖图只看了 dependencies 与 peerDependencies。devDependencies 里的内部依赖未计入，所以实际的构建期耦合可能比图上更多。
§5 Takeaway 拿走什么
  • 读一个陌生 monorepo，先画依赖方向图和行数分布，再读代码。两条信息就能定位重心和分层，比读 README 快。 适用条件：包数量 > 3。单包仓库直接读入口。
  • 把稳定性承诺写在 README 第一行。「Experimental，可能移除」一句话省掉所有关于 semver 的争论。 适用条件：你发布了尚未稳定的包。比不发布或藏在 0.x 版本号里都好。
  • 渲染层零依赖，是 headless 能力的结构前提。如果你的 UI 库反向依赖了业务逻辑，无头模式就只能靠 mock 拼出来。 适用条件：你需要同时支持 TUI / API / 服务端。
