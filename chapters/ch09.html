§1 Mental Model 一句话心智模型

先记住这一句

pi-ai 用 39 家 provider 换来一个统一 API，代价藏在一个容易忽略的地方：模型清单根本不在仓库里。它是构建时从上游目录拉取的产物，.gitignore 掉了。

这层抽象要解决的问题不只是「请求格式不同」。真正难的是三件事：认证方式各不相同（API key / OAuth / 订阅账号 / 云厂商 IAM）、流式事件语义不同、以及模型能力矩阵每周都在变（上下文窗口、价格、是否支持 thinking、是否支持工具）。

前两件靠代码解决，第三件靠不把它当代码——生成、不入库、构建时刷新。

一条显式的收录标准

库只收支持 tool calling 的模型。ai/README.md:5 这一句把 pi-ai 从「通用 LLM SDK」区分了出来——它是 agent 的基础设施，不是中立的多家封装。

认证：显式值永远赢

调 models.stream() 时，认证经由所属 provider 解析并合并进请求；每次请求里显式给的值永远优先（环境变量、存储的凭证、OAuth token 都排在后面）。ai/README.md:330

并且解析结果可以不发请求就查——models.getAuth(provider) 或 getAuth(model)。对一个要同时支持 API key、OAuth 订阅、云厂商凭证的库来说，「能单独查认证怎么解析出来的」是必要的可调试性。

这也解释了 第 03 章里循环为什么要 getApiKey 回调：OAuth token 会过期，而一个 run 可能跑很久，认证必须在每次 LLM 调用时重新解析，不能在构造时固定。

§3 Design 设计动机与权衡

把模型元数据当构建产物，而不是源码

好处：模型清单每周都在变（新模型、改价、改窗口），入库会让 git 历史里塞满与代码无关的数据变更，而且永远滞后。构建时刷新意味着发版时的清单总是新的。

代价有三条，都很实在：

  • 克隆下来不联网就构建不了（除非已有一份快照可供 build:offline）。
  • 构建结果不可复现——同一个 commit 在不同日期构建，产出的模型清单不同。发布源码归档里带上数据，正是为了补这个洞。
  • 上游目录挂了或改格式，构建就挂。

与 第 16 章那套「依赖精确锁版本、拒绝同日发布」的谨慎相比，这里的取舍是反向的：依赖代码要钉死，模型数据要最新。区分依据是——依赖代码会执行，模型元数据只是数据。

为什么值得自己写，而不是用现成的多 provider 库

5.8 万行是很大的投入。从收录标准（只要支持 tool calling 的模型）和认证设计（订阅账号、OAuth）能看出理由：通用库优化的是「换 provider 容易」，agent 需要的是「工具调用、流式、成本、thinking 级别在所有 provider 上语义一致」——后者要深入到每家的细节里去抹平，而不是找最大公约数。

这个判断是否值 5.8 万行，取决于你要支持几家。支持 2 家不值，支持 39 家大概值。

§4 Limits 边界与失效条件
  • 「39 个 provider」是按 *.models.ts 文件数统计的，其中若干是同一家的不同接入方式（如 openai / openai-codex / azure-openai-responses），也包含若干区域变体（minimax / minimax-cn）。真实的「厂商数」小于 39。
  • 构建可复现性依赖发布归档。直接从 git checkout 构建，产物与官方发布不保证一致。
  • 模型能力矩阵的正确性取决于上游目录。上游标错了窗口大小，pi 就跟着错，而 第 06 章的压缩阈值直接依赖这个数字。
  • 不收录不支持 tool calling 的模型是设计选择而非疏漏。想用纯对话模型跑 pi，路径是自定义 provider（docs/custom-provider.md），不是等它被收录。
§5 Takeaway 拿走什么
  • 区分「会执行的依赖」和「只是数据的依赖」，用相反的策略。前者钉死版本、拒绝新鲜；后者构建时刷新、要最新。 适用条件：你依赖会频繁变化的外部目录（模型清单、汇率、地区码）。但要为可复现构建准备一份归档快照。
  • 认证解析要能「不发请求就查」。多种认证方式共存时，「到底用了哪个凭证」是最常见的支持问题。 适用条件：支持两种以上认证方式。
  • 在每次请求时重新解析认证，而不是在客户端构造时固定。OAuth token 会在长任务中途过期。 适用条件：支持 OAuth 或任何有效期凭证。纯 API key 场景固定下来更简单。
