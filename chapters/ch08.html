§1 Mental Model 一句话心智模型

先记住这一句

Harness v2 不是「pi 的架构」，是「pi 正在长成的架构」。存储底座已经完工并通过三后端一致性测试；执行器是一个刻意做成会抛错的空壳。中间隔着 30 个还没做完的工作包。

锚点之后本章的判定锚定在 ac4ac9e（2026-08-07），在那个版本上依然成立。上游在那之后已经实现了执行器的大部分方法，但默认 CLI 没有切换过去——「执行器是空壳」不再是上游的现状。本书没有换锚点，变化见本章末尾的 追记。

这是全书最容易被误读的一章，也是本书存在的主要理由。上游有一份 3437 行的设计文档，写得极其详尽——lanes、records、checkpoints、race catalog、drive modes。任何人读完都会以为那就是 pi 的样子。但读者在自己机器上跑的 pi，走的是 第 03 章 那个循环。

更要紧的是别把「空壳」读成「没做完」。空壳是一个已经验收的工作包的产物：设计文档明确要求未完成的方法必须抛错，而不能返回看似合理的空快照。这是一种质量决定，不是进度落后。

§3 Design 设计动机与权衡

「宁可抛错，不要看似成功」

F0 的验收标准值得任何做大重构的人抄走：未完成的方法必须以可识别的方式失败，不能返回空快照、idle 状态或 no-op 成功。

理由在多 agent 并行开发的语境下特别硬：如果 lanes() 暂时返回 []，另一个包的作者会写出「没有 lane 时走这条路」的逻辑，并让测试通过——一个建立在假象上的实现，等 lanes() 真正实现时才暴露。抛错则让依赖关系在编译期与测试期立刻显形。

代价是 AgentHarness 目前完全不能用，连「试试看」都不行。他们接受了这个代价，并把它写进了验收标准。

为什么先做存储再做执行

存储契约定错，上层全部重写；执行器可以在稳定契约上分包替换。所以顺序是：定义 record → 三后端实现 → 一致性测试锁死 → 才轮到执行器。

这也解释了一个外部观察者容易误判的现象：看起来「一年了 harness 还没做完」，实际是底座做完了而门面还没动。门面（22 个方法）恰恰是最后才动的部分，因为它消费所有其它包。

把 spec 当任务队列，值得吗

好处很明显：41 个包的依赖关系、主文件、验收标准全部写在一处，新 agent（人或 AI）读一份文档就能开工，认领冲突用 git 解决。

成本也很明显：一份 3437 行、每次认领都要改的文档，本身就是热点文件。而且它同时承担两种职责——「系统应该是什么样」和「谁在做哪块」。前者应该稳定，后者每天在变。文档里已经能看到两者的摩擦：J 轨的所有权标记写着「这项工作在计划被拆成 J0–J6 之前就开始了」，需要一段专门的散文解释历史。harness-v2.md:3260

§4 Limits 边界与失效条件

读这一章时要小心什么

  • 这一章的保鲜期最短。41 个包在动，本书锚定的是 ac4ac9e。「11/41」这个数字在你读到时几乎肯定已经变了；不变的是判定方法——数 - [x]、数 unavailable() 调用、grep new Agent(。
  • 「部分落地」是对整章的裁决，不是对每个构件的。同一份文档里，session 存储是已发布，lanes/checkpoints/drive modes 是仅设计文档。第 07 章与本章的状态徽章不同，正是因为它们描述的是这份设计的不同层。
  • 设计文档不承诺会被实现。没有任何机制保证 30 个未完成的包会完工；它们是计划，不是承诺。把 lanes 当成「pi 的能力」来做技术选型，是拿别人的路线图当自己的依赖。
  • 即便全部完工，CLI 也不自动受益。文档显式把 packages/coding-agent 排除在迁移范围外。harness-v2.md:3169

检查过并确认的反面证据：packages/evals/src/pi-harness.ts 里的 "Harness" 是 evals 框架自己的同名类型，与 AgentHarness 无关；packages/protocol/src/schemas.ts 仅在一行注释里提到 AgentHarnessPhase。schemas.ts:37 二者都不构成生产消费者。

§5 Takeaway 拿走什么
  • 大重构时，让未完成的接口抛专有异常，而不是返回貌似合理的默认值。并把「没有任何未完成方法报告看似成功」写成可执行的验收测试。 适用条件：多人/多 agent 并行开发同一个新接口。单人顺序开发时，空实现的危害小得多。
  • 自底向上重写：先锁存储契约，再换执行器。并且用一套跨实现的一致性测试把契约钉死，否则「契约」只是第一个实现的行为。 适用条件：存储格式会变。如果只换执行逻辑、存储不动，这个顺序无意义。
  • 评估一个开源项目时，先区分「文档描述的系统」和「运行的系统」。方法很机械：找到生产入口的构造点，从那里往下读；文档里读不到的分叉，代码里一 grep 就现形。 适用条件：项目处于活跃重写期。成熟稳定的项目里文档与代码通常同源。
  • 如果要把 spec 当任务队列，考虑把「设计」和「谁在做」拆成两份文件。前者该稳定，后者每天在变；合在一起会让设计文档变成高冲突热点。 pi 没这么做，用「reserve 提交单独落 main」缓解了冲突——代价是每次认领都要一次往返 main 的提交。
