04 工具执行 「并行」不是你以为的那个并行

已发布 主文件 agent-loop.ts L411–L791 内建工具 7 个
§1 Mental Model 一句话心智模型

先记住这一句

pi 的「并行工具执行」只并行 execute() 本身。参数校验、beforeToolCall 拦截、事件发出的第一帧，全部按 assistant 给出的顺序串行走完，一个都不跳。

这句话是理解本章所有行为的钥匙。一次 tool batch 被拆成三个阶段，只有中间那段是并发的：

  • preflight（串行）——找工具、规整参数、schema 校验、跑 beforeToolCall。这一段决定「哪些调用有资格执行」。
  • execute（可并发）——真正跑工具体。只有这里是 Promise.all。
  • finalize + 落序（串行）——跑 afterToolCall、生成 toolResult 消息。消息顺序强制回到 assistant 的源顺序，与谁先跑完无关。

由此得到一条实用推论：事件顺序和消息顺序是两套顺序。tool_execution_end 按完成先后到达（UI 据此实时更新），而进入会话历史的 toolResult 永远按模型写下的顺序排列（模型据此理解因果）。把这两者当成一回事，是接 UI 时最常见的错。

§2 Evidence 代码实证

模式选择：一票就能把整批拖回串行

并行分支里，真正并发的只有一小段

executeToolCallsParallel 的循环体本身是 await 串行的：它逐个 emit tool_execution_start、逐个跑 prepareToolCall，只把「执行 + finalize」包成闭包推入数组而不立即 await。agent-loop.ts:489 agent-loop.ts:522

并发发生在循环之后的那一行，随后立即按数组原序生成消息：agent-loop.ts:540–548

packages/agent/src/agent-loop.ts改写自 L540–L549
const orderedFinalizedCalls = await Promise.all(          # 唯一的并发点
    finalizedCalls.map((e) => typeof e === "function" ? e() : Promise.resolve(e)),
);
const messages: ToolResultMessage[] = [];
for (const finalized of orderedFinalizedCalls) {          # 回到 assistant 源顺序
    const toolResultMessage = createToolResultMessage(finalized);
    await emitToolResultMessage(toolResultMessage, emit);
    messages.push(toolResultMessage);
}
这是改写：省略了变量的完整类型标注与箭头函数体的换行。Promise.all 保序，所以 orderedFinalizedCalls 的下标仍是源顺序——「按完成顺序发事件、按源顺序存消息」就是靠这一点实现的。

preflight 的四道关

prepareToolCall 顺序执行四步，任一步失败都返回 kind: "immediate"——不进执行阶段，但仍然会产出一条 toolResult，模型总能看到发生了什么。agent-loop.ts:600

步骤失败时位置
① 按名字找工具Tool {name} not foundagent-loop.ts:607
② prepareArguments 规整参数（可选钩子）抛错即成为错误结果agent-loop.ts:586
③ schema 校验（typebox）校验信息回给模型agent-loop.ts:618
④ beforeToolCall 可 block用 reason 作为结果，可带 terminateagent-loop.ts:636

注意③在④之前：beforeToolCall 拿到的是已经过 schema 校验的参数，不是模型的原始输出。想做「参数级安全策略」的扩展因此不必自己重做解析，但也看不到那些没通过校验的调用——它们在④之前就被挡掉了。

工具抛错不是异常，是一种正常结果

executePreparedToolCall 把 execute() 的异常整个吞掉，转成 isError: true 的结果。agent-loop.ts:670 循环不会因为工具失败而中断——这是 agent 能自我纠错的前提。

同一函数里有一处容易忽略的细节：工具通过 onUpdate 推送的进度事件被收集进 updateEvents 数组，并用 acceptingUpdates 标志在执行结束的瞬间关闸，然后 await Promise.all(updateEvents) 才返回。agent-loop.ts:683–699 效果是：迟到的 tool_execution_update 永远不会排在该工具的 tool_execution_end 之后，UI 不会出现「已完成又冒出进度条」。

afterToolCall 只能改结果的四个字段

后置钩子的返回值被逐字段合并，未提供的字段保留原值；钩子自己抛错则整条结果被替换为错误。agent-loop.ts:724–751 可改的是 content / details / usage / terminate（外加 isError）——改不了 toolName、toolCallId，也无法凭空追加一条结果。

最后 createToolResultMessage 里有一行注释值得记住：JS 扩展写的无类型工具可能返回没有 content 的结果，此处兜底成空数组，避免 null 流进会话历史和 provider 请求体。agent-loop.ts:782–784 这是「核心必须容忍扩展写得不严谨」的具体体现，参见 第 12 章。

§3 Design 设计动机与权衡

为什么 preflight 不并行

把校验也并行，吞吐会更好一点。不并行换来的是一个确定的拦截顺序：beforeToolCall 按源顺序依次看到每个调用，因此可以实现有状态的策略（「这一批里已经批准过一次写操作了，第二次要问」）。如果 preflight 并发，钩子就得自己处理竞态，而钩子是扩展作者写的。

这个取舍与 第 03 章看到的一致：pi 倾向于把复杂度留在核心、把简单契约给扩展，代价是核心的控制流不可配置。

「一个串行工具拖垮整批」是特性还是缺陷

从实现看这是刻意的：判断写在批次级别而非调用级别。agent-loop.ts:422 理由推得出来但未见公开论述：标 sequential 的工具通常是有副作用且顺序敏感的（改文件、跑命令），如果只把它自己串行、其它照并发，它与并发工具之间的交错顺序仍然不确定——那等于没解决问题。要真正确定，只能整批串行。

代价是可观的：模型常在一条消息里发出「读三个文件 + 编辑一个文件」，只要 edit 是串行的，三次读也失去并发。pi 的内建 edit/write 用的是另一条路——file-mutation-queue.ts 这样的串行化队列，把顺序保证做在工具内部而不是抬到批次级别。

错误一律回灌给模型，而不是抛给用户

找不到工具、参数不合法、执行抛错、被 beforeToolCall 拦下——四种情况产出的都是一条正常的 toolResult。这让「模型自己发现错了再改」成为默认路径，而不是需要额外设计的功能。

边界在于：这也意味着没有任何一类工具错误会让 run 停下来。一个每次都失败的工具，模型可以反复调用它直到上下文耗尽。停机责任完全在模型和上层（见 第 03 章 §4）。

上游公开谈过工具——谈的是「选择」那一半

Earendil《What is a Harness?》（2026-08-20）——发布于本书锚定 SHA 之后 13 天——给出一条工具通则：「Critically, the harness usually does not dictate when and how the AI model should use the tool.」harness 通常不规定模型何时、如何使用工具，只把它们提供出来、描述清楚，交给模型自己判断。

这条通则在它自己的抽象层级上是准确的，pi 的代码也印证了它的核心：preflight 第一步查表时，键就是模型写下的那个 name。agent-loop.ts:607 工具集由 harness 给定，选哪一个由模型的输出决定。本章的贡献是指出它下面还有一层——按 pi 的实现收窄，更准确的说法是：选择权归模型，执行权几乎全归 harness。模型写下一批 tool call 之后，对接下来发生的事几乎没有发言权：

  • 这批是并发跑还是一个接一个跑，由 harness 在批次级裁定；判定只读 config 与工具自带的 executionMode，模型无从表达偏好。agent-loop.ts:422
  • 某一次调用会不会真的执行，beforeToolCall 能在执行前否掉，模型只拿到一句 reason。agent-loop.ts:636
  • 工具返回的内容也未必是模型看到的内容——afterToolCall 逐字段改写结果，可改的包括 content 与 terminate。agent-loop.ts:724–751

这个区分决定了工具层的工作量估算落在哪里。照通则去理解，工具层像一件文档工作：schema 写对、描述写清楚，模型自会用好。而本章读到的代码说明，工具层真正的复杂度是在模型做完决定之后才开始的——顺序保证、拦截时机、错误回灌、事件与消息的两套顺序，这几件事没有一件能靠把工具描述写得更清楚来解决。

这不是疏漏，而是抽象层级的选择：科普不是规格说明。也正因如此，本书只把它当作上游意图的证据，不当作代码行为的证据。本章前面对批次级串行判定所标的「未见公开论述」不受影响——文章没有触及执行侧的任何决定。

§4 Limits 边界与失效条件

什么时候这套机制会咬你

  • 并发工具之间没有任何互斥。循环层不提供锁。两个并发工具同时写一个文件，结果取决于工具自己有没有做序列化。内建写工具有 file-mutation-queue，扩展工具默认什么都没有。
  • signal.aborted 的检查点是稀疏的。并行分支在每次 push 闭包后检查一次并 break，agent-loop.ts:522–538 但已经 push 进去的闭包仍会在随后的 Promise.all 中运行。abort 之后仍有工具在跑，是预期行为——真正的取消要靠工具自己响应 signal。
  • preflight 抛错的粒度是整个调用，不是单个字段。schema 校验失败时模型拿到的是校验器的信息；工具参数设计得越复杂，模型越难从这条信息里恢复。
  • afterToolCall 抛错会吃掉工具的成功结果。agent-loop.ts:747–750 一个写得不严谨的审计钩子，能把所有工具结果变成错误。钩子自身必须防御性编写。

检查过但未发现问题：串行分支与并行分支的错误处理路径一致（都经 prepareToolCall → executePreparedToolCall → finalizeExecutedToolCall），没有出现「只在某一种模式下才有的行为」。两个分支的差别只在于何时 await。

§5 Takeaway 拿走什么

如果你在设计工具执行层

  • 把「事件顺序」和「历史顺序」显式分开，并在文档里写清哪个是哪个。UI 要实时性，模型要因果性，两者天然冲突；pi 用「并发拿结果、按源序落消息」同时满足。 适用条件：允许并行 tool call 且有实时 UI。无 UI 的批处理场景只需要一种顺序。
  • 顺序保证做在工具内部，别抬到批次级别。pi 的批次级 sequential 开关会让同批无关工具一起失去并发；内建写工具走的 mutation queue 才是可扩展的做法。 适用条件：你的工具集里有副作用工具。纯只读工具集不需要任何序列化。
  • 所有工具错误都变成模型能读的 toolResult，包括「工具不存在」和「被策略拦下」。这让自我纠错成为默认行为而非附加功能。 代价：没有任何工具错误能终止 run，停机保护必须另外做。
  • 给进度回调设一个「关闸」标志，并在返回前 await 已排队的事件。否则迟到的进度事件会排在完成事件之后，UI 出现无法解释的回跳。 适用条件：工具支持流式进度。一次性返回的工具不涉及。
