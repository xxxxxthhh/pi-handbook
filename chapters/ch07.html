07 会话持久化 会话不是一条链，是一棵树；而且现在有两个版本并存

已发布 CLI 格式 v3 新栈格式 v4 后端 3 个，同一套一致性测试
§1 Mental Model 一句话心智模型

先记住这一句

pi 的会话是一个只追加的 entry 序列，每条 entry 带 id 和 parentId——所以它物理上是日志、逻辑上是树。你看到的对话，只是从某个叶子往根走的一条路径。

这一个设计决定同时解释了三件事：

  • /tree 能来回跳。切分支就是换一个叶子指针，不需要改写任何已有数据。
  • 压缩不可撤销但可回放。压缩写的是一条新 entry（第 06 章），旧消息物理上还在文件里，只是不在当前路径上。
  • 崩溃最多丢最后一条。追加写 + 每行一个 JSON，坏行不会污染前面的内容。

要小心的是：「会话文件里有」不等于「模型看得到」。文件是全树，上下文是一条路径，而路径还要再过 第 05 章 的两道闸。

§2 Evidence 代码实证

entry 的五个公共字段

packages/agent/src/harness/session/types.ts原文 L14–L20
export interface EntryBase {
    type: string;
    id: string;
    seq: number; // shared sequence; read-side, storage-assigned
    parentId: string | null; // storage-assigned: the appending lane's leaf
    timestamp: number; // Unix ms, storage-assigned
}
三个字段标着 storage-assigned：seq、parentId、timestamp 都由存储层填，调用方给不了。parentId 取「当前 lane 的叶子」——树结构因此是追加的副产品，不需要调用方维护。

树的形状不由任何人显式声明：你在哪个叶子上追加，新 entry 的父就是谁。types.ts:18 分叉发生在「把叶子指针移回中间某个 entry，然后继续追加」的那一刻。

这不是历史遗留，是正在进行的迁移的当前状态。harness-v2 设计文档把「旧 v3 会话必须能打开并恢复到 idle」列为唯一的向后兼容要求，其余格式和 API 全部允许破坏。harness-v2.md:3 完整判定见 第 08 章。

v4 日志里有两类东西：entry 和 record

JSONL 编解码器维护两个类型集合，一个是对话内容，一个是执行痕迹：codec.ts:7 codec.ts:16

entry（7 种）record（9 种）

给谁看模型 + 用户 + 回放崩溃恢复

fork 的两种作用域

packages/agent/src/harness/session/types.ts原文 L359
export type ForkOptions = { scope?: "branch"; entryId?: string; position?: "before" | "at" } | { scope: "tree" };
"branch"：只复制到某个 entry 为止的那条路径。"tree"：整棵树。position 决定分叉点落在目标 entry 之前还是就在它上面。

两种作用域对应两种意图：「从这里另起一条路试试」用 branch，「把整个会话另存一份」用 tree。类型层面用联合类型强制二选一——选了 tree 就不能再指定 entryId，因为那没有意义。

§3 Design 设计动机与权衡

为什么是日志而不是「保存当前状态」

把当前对话序列化成一个 JSON 数组、每次覆盖写，实现更简单。选择追加日志换来的是：崩溃只丢最后一行而不是整个文件；写入是 O(1) 而不是 O(会话长度)；以及最关键的——树结构几乎免费。覆盖式存储要支持分支，就得自己实现版本管理。

代价是读取要重放：打开一个长会话必须扫全文件再归约出当前路径。SQLite 后端存在的意义正在于此——同样的接口，把「扫全文件」换成索引查询。

为什么先做存储、后做执行

这是 harness-v2 迁移最值得学的一点：durability 的底座（record 类型、三后端、一致性测试）已经全部落地并通过测试，而消费它的执行器还是空壳（第 08 章）。

顺序是有道理的。存储契约一旦定错，上层全要重写；而执行器可以在稳定的存储契约上分步替换。先把「怎么记录」定死并用一套一致性测试锁在三个实现上，再谈「怎么执行」——这是自底向上重写的标准做法，也是它进度看起来慢的原因。

「唯一的兼容承诺」是一种成本控制

设计文档明说：只保证旧 v3 会话能打开并恢复到 idle，其余格式和 API 全部可破坏，不写迁移、不做 schema 版本化、不提供转换路径。harness-v2.md:3

把兼容承诺压缩到一条，重写的自由度就最大化了。这个选择的前提是用户数据只有一类值得保（历史会话），其余（内部 API、SQLite schema、record 格式）都还没有外部依赖者——对一个一岁的项目成立，对一个五岁的项目多半不成立。

上游自己怎么说：会话是用户的资产

上面三小节的理由全是从代码和 harness-v2.md 这份内部工程文档反推的，「上游公开说过什么」这一格一直空着。锚定 SHA 之后 13 天，Earendil 发了立场文 《What is a Harness?》（2026-08-20）：用户能在自己机器上跑自己的 harness，就保住了把工具变成自己的自由，以及 "keep local copies of the sessions that over time will constitute their correspondence with machines"。这是立场文，不是代码也不是仓库文档——它只能证明上游怎么讲自己的产品，证明不了任何一行代码为什么这么写。

它补上的坐标是：会话在上游叙事里是用户侧的通信录，不是厂商侧的用量日志。对得上的实现有两处——会话按 cwd 编码落在用户自己盘上的 ~/.pi/agent/sessions/ 下 session-manager.ts:474，文件是只追加的明文 JSONL 树 session-manager.ts:845。跳回旧分支、拿别的工具翻历史，都不经过服务端。

一致不等于因果，而且这两处的一致程度并不一样。「留在本机」是接口层面的：§2 那三个后端（内存 / JSONL / SQLite）都落在本机。「明文可读」只是当前默认后端的性质，不是契约——同一套一致性测试判定 SQLite 后端同样合格，而 SQLite 文件不是明文。换句话说：CLI 默认后端哪天换成 SQLite，存储契约一个字不用改，而「用 grep 读自己的会话」就没了。被锁死的是本地，不是可读。追加日志这个形状，本节开头已有更直接的解释（崩溃只丢最后一行、写入 O(1)、树免费），它们不需要产品意图也成立，不能倒过来算成意图的产物。

§4 Limits 边界与失效条件
  • 单写者假设。设计文档把「一个会话同时被两个进程写」列为非目标，恢复逻辑把单写者产生不了的状态直接当作损坏。harness-v2.md:32 在同一目录跑多个 pi 会话是受支持的（各自独立会话文件），但让两个进程写同一个会话不是。
  • 长会话的读取成本随长度线性增长（JSONL 后端）。树越大，重放越慢。SQLite 后端是给这个问题准备的答案，但 CLI 默认仍是 JSONL。
  • v3 不记录执行痕迹。今天 CLI 写的会话文件里没有 record，所以即便 AgentHarness 完工，历史会话也无法「恢复未完成的 run」——只能恢复到 idle。这正是兼容承诺措辞里 "restore idle" 三个字的含义。
  • 压缩后的旧消息仍占磁盘。会话文件只增不减。压缩省的是 token，不是存储。

检查过但未发现问题：三个后端跑同一套一致性测试，且该套件覆盖 record 的追加、查询与非法查询拒绝（如 limit: 0、类型与 operationKind 冲突的组合）。conformance.ts:242–244 这类「三实现共用一套测试」的结构，是本章所有断言里我最有信心的部分。

§5 Takeaway 拿走什么
  • 会话存成带 parentId 的追加日志，树结构就是免费的。分支、回退、fork 全都变成「移动叶子指针」，不需要任何版本管理机制。 适用条件：你想支持对话分支或回退。纯线性对话用数组更简单。
  • 把「对话内容」和「执行痕迹」分成两类记录。前者给模型和用户，后者给崩溃恢复。混在一起会让回放逻辑必须理解执行细节。 适用条件：你要做崩溃恢复。不做恢复就不需要 record，v3 就是这么活下来的。
  • 多后端时，先写一套一致性测试，再写第二个实现。pi 的三个后端共用一份 createSessionBackendConformance——这是「新后端不会悄悄少实现一半语义」的唯一保证。 适用条件：存储后端可插拔。单一后端时这套测试就是普通单测。
  • 重写时把向后兼容压缩成一条明确的承诺，并写进设计文档。「只保证旧会话能打开」比「尽量兼容」可执行得多——后者会在每个 PR 里重新争论一次。 适用条件：外部依赖面还小。已有大量下游 API 使用者时，这个自由度不存在。
