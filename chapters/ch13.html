§1 Mental Model 一句话心智模型

先记住这一句

「自扩展」在 pi 这里不是宣传语，是一个可验证的闭环：仓库自己的 .pi/ 目录里装着 4 个扩展和 5 个 prompt，pi 的维护者用它们开发 pi。其中一个扩展的职责，是把 CI 里 pi 分析 issue 产生的会话导入到本地复现。

判断「self-extensible」是不是空话，最快的方法不是读 README，是看项目自己用不用。

把这两端接起来，闭环是：issue 打标签 → CI 用 pi 分析 → 会话作为 gist 发布 → 维护者用 pi 的一个扩展把该会话导入本地 → 在本地继续那次调查。会话（第 07 章）在这里成了 CI 与本地之间的交换格式。

prompt 模板也是仓库资产

.pi/prompts/*.md 是可被 /名字 调用的 prompt 模板，带 YAML frontmatter（description、argument-hint）。以 sa.md（更新安全公告）为例，它写了完整的调查流程、CVSS 讨论步骤、草稿格式、以及一组安全规则——包括「不要用浏览器会话或 cookie 去抓公告评论」和「绝不假装读过评论」。

这类模板与 第 17 章的 AGENTS.md 属于同一类资产：把重复性的、容易出错的工作流固化成文本，交给 agent 执行。区别是 AGENTS.md always-on，prompt 模板按需调用。

§3 Design 设计动机与权衡

「项目自己用」是最强的可用性证据

一个扩展系统可以很完备但没人用。.pi/ 目录的存在把这个问题变成可验证的：4 个扩展全是为解决维护者真实痛点而写的（重绘卡不卡、token 速度多少、issue 怎么复现），不是示例代码。

更进一步：redraws.ts 只有 24 行。一个 24 行就能解决真实问题的扩展 API，比 2988 行文档更能说明它好不好用。

会话作为交换格式

import-repro 这条链路依赖一个前提：会话是可移植的文件。第 07 章的 JSONL 设计在这里兑现了一个当初未必是主要目标的收益——CI 环境里的一次调查，可以原样搬到开发者机器上继续。

需要处理的差异只有 cwd（CI 的检出目录是高熵路径），扩展做的正是重写这一项。这说明会话文件里与环境耦合的东西很少，是个好设计的旁证。

与 README 的「让 agent 自己解释自己」

README 说文档可以读，「但你也可以直接让 agent 解释它自己」。配合 skills 文档那句「pi 可以创建 skill」，这里有一个一致的姿态：把 agent 当作接触这个代码库的界面之一。

这个姿态的可信度取决于代码库对 agent 友好的程度——而 AGENTS.md、.pi/prompts/、以及 第 19 章那套机读的工作包协议，都是在为此铺路。

§4 Limits 边界与失效条件
  • 4 个扩展是个小样本。它们证明了 API 可用，但没证明 API 覆盖了多样的需求。examples/extensions/ 下另有若干示例（subagent、plan-mode、doom-overlay 等），那些更接近能力展示而非日常使用。
  • .pi/ 里的扩展要项目被信任才加载。clone 下来第一次跑 pi 并拒绝信任，这些扩展不会生效（第 15 章）。
  • 「让 agent 解释自己」的质量无法验证。本书不评估这条路径的实际效果——它取决于模型、上下文预算和提问方式，不取决于仓库。
  • prompt 模板中的操作指令是给 agent 的，不是可执行代码。sa.md 里那些安全规则（不许用 cookie 抓评论、不许假装读过）靠模型遵守，与 第 17 章 的 AGENTS.md 是同一种赌注。
§5 Takeaway 拿走什么
  • 想验证一个扩展系统好不好用，看项目自己的配置目录，不看文档长度。24 行解决真实问题的扩展，胜过 3000 行 API 参考。 适用条件：评估任何可扩展工具。这是本章最实用的一条判据。
  • 让会话成为可移植文件，CI 与本地之间就多了一条调查交接的通路。前提是会话里与环境耦合的字段足够少。 适用条件：你在 CI 里跑 agent。需要会话格式先做到环境无关。
  • 把重复且易错的工作流固化成 prompt 模板，放进仓库。它与 always-on 的规则文件互补：规则管日常纪律，模板管特定流程。 适用条件：存在「每次都要按同样步骤做」的运维任务（发安全公告、写 changelog、审 PR）。
